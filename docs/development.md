# Development and extension guide

## Repository structure

```text
.
├── index.html                  # Main menu and navigation handlers
├── tutorial.html               # Static gameplay and control instructions
├── game.html                   # Loader, pause/game-over overlays, and script tags
├── main.js                     # Application entry point and frame orchestration
├── world.js                    # Environment, lights, lanes, spawning, and movement
├── player.js                   # Articulated player hierarchy and player Box3
├── animations.js               # Tween.js character animation sequences
├── controls.js                 # Keyboard state and movement dispatch
├── collisions.js               # Box3 tests, score, lives, invulnerability, game over
├── loader.js                   # OBJ/MTL and glTF loader wrappers
├── assets/                     # Runtime and unused source assets
├── libs/                       # Vendored Three.js, Tween.js, loaders, and utilities
├── css/                        # Committed browser styles
├── scss/style.scss             # Loading-animation SCSS source; no compile script included
├── hierarchical-model-graph/   # Project/model diagrams
├── report/report.pdf           # Original 2021 project report
└── docs/                       # Maintained technical documentation
```

The application uses plain JavaScript ES modules. The checked-in Three.js build identifies itself as revision `131dev`; the Tween.js bundle identifies itself as version `18.6.4`. There is no `package.json`, lockfile, Makefile, build configuration, test configuration, service worker, backend, or environment-variable file.

## Running locally

### Requirements

- A modern desktop browser with WebGL and JavaScript-module support.
- A keyboard for gameplay.
- A static HTTP server. Python 3 is sufficient and does not become a project dependency.

The repository must be served over HTTP. Browsers commonly block ES-module imports or asset requests opened from `file://`.

### Python example

Keep the checkout directory named `NinjaAndLava`, enter it, and serve its parent:

```bash
git clone https://github.com/ErNikki/NinjaAndLava.git
cd NinjaAndLava
python3 -m http.server 8000 --directory ..
```

Open:

```text
http://localhost:8000/NinjaAndLava/
```

On Windows, `py -m http.server 8000 --directory ..` is the equivalent when the Python launcher is installed.

Serving the parent is necessary because `game.html` uses absolute script URLs:

```html
<script src="/NinjaAndLava/libs/tween.umd.js"></script>
<script type="module" src="/NinjaAndLava/main.js"></script>
```

Serving from inside the repository at `/` would make those requests point to a nonexistent `/NinjaAndLava/` child. Renaming the checkout also requires changing the URLs or hosting it at a matching route.

Normalize.css is loaded from cdnjs. If that request is unavailable, the project's own styles and JavaScript assets remain local, but browser-default CSS normalization may differ.

## Build and dependency model

There is no build step. Development consists of editing the committed HTML, CSS, and JavaScript files and refreshing the browser.

`scss/style.scss` corresponds to the loading animation, but no Sass command or dependency is recorded. `css/loadingScreen.css` is the file actually linked by the browser, so changing only the SCSS has no runtime effect until CSS is generated by an external tool.

The following are imported but unused by the current game entry point:

- `Stats` from `libs/stats.module.js`;
- the dat.GUI module from `libs/dat.gui.module.js`.

Do not add npm installation instructions unless a package manifest and a reproducible workflow are added to the repository.

## Manual verification

There is no automated test suite. A useful smoke test is:

1. Start a parent-directory HTTP server and open `/NinjaAndLava/`.
2. Confirm that **New Game** and **Tutorial** navigate correctly.
3. Wait for the loading overlay to disappear and confirm that the canvas and `HEARTS: 3 / SCORE: 0` HUD appear.
4. Exercise left/right movement, jumping, and camera presets.
5. Press `Esc`, confirm that the frame loop pauses, and resume with the button.
6. Verify that a star changes score, a spike changes lives and starts the red blink, and a heart increases lives.
7. Confirm that three net hits show game over and that Restart performs a full reload.
8. Inspect the browser console and network panel for missing OBJ, MTL, glTF, binary, or texture files.

During documentation validation, the project was served with Python's static server from the parent directory. The menu, initial loading flow, WebGL scene, HUD, pause/resume flow, automatic collisions, game-over overlay, and reload-based restart all executed in a Chromium-based browser without console errors. The full initial load took several seconds locally because of the cave-model setup.

## Deployment

The public project URL is:

**https://ernikki.github.io/NinjaAndLava/**

The repository is directly deployable as static files under the `/NinjaAndLava/` project path. The absolute script URLs in `game.html` couple the runtime to that path.

The checkout contains no `.github/workflows` directory, Pages action, deploy script, `gh-pages` branch, CNAME, Jekyll configuration, or build output directory. Git records `main` as the local branch tracking `origin/main`, but the GitHub Pages source-branch setting is repository metadata and cannot be established from the files themselves. The implementation therefore verifies a static, no-build deployment, not which Pages source setting is selected.

The live site was also smoke-tested while preparing these docs: the menu and game route were reachable and no browser console errors were reported. Its asset-heavy loading screen remained visible much longer than the local run before the game canvas appeared.

`game.html` contains `<base href="{{NinjaAndLava}}">`, and `tutorial.html` contains the older `<base href="{{final-project-sernii-team}}">`. The current absolute game script URLs and tested project path work, but these unresolved placeholders are fragile if the site is moved. A future deployment cleanup should replace them with a deliberate base path or remove them after converting resource URLs consistently.

## Extending the game

The current code favors direct edits over registries or data-driven configuration. The steps below reflect that implementation; a larger extension should first remove duplicated type and lane logic.

### Add an obstacle

1. Add its model and material files under `assets/` and document their source and license.
2. Add a loader wrapper in `loader.js`, following the `SpikeBall` pattern. Put the loaded hierarchy under the supplied wrapper so `WorldObject` movement and `Box3` generation continue to work.
3. Add a type constant to both `world.js` and `collisions.js`; these values are currently duplicated and must stay aligned.
4. Add the type to `WorldObject.randomSpawn()` with explicit, non-overlapping probability intervals.
5. Handle the type in each of the three collision switch statements, or preferably refactor those repeated loops into one shared handler first.
6. Decide whether collision hides the wrapper, records it only, changes invulnerability, and returns from the frame.
7. Verify that passed instances are cleaned up if the new type is expensive.

### Add a collectible

Follow the star/heart loader and spawn path, then store any new state in `CollisionsDetector` and expose a getter for the HUD. Hide and record the wrapper on collection so it cannot apply twice. Add its DOM display in `main.js` after the loading manager completes.

If the collectible should work during invulnerability, the collision architecture must change: the current outer `if (!invulnerableFlag)` skips every type, not only spike damage.

### Add or change lanes

Lane count is not centralized. A new lane requires coordinated changes to:

- the `Right`, `Left`, and `Center` index constants and three arrays in `world.js`;
- spawn x positions and `SpawnObj()` routing;
- `ShouldISpawn()` and `Update()` lane loops;
- the matching constants and loops in `collisions.js`;
- exact x cases in `ControlManager.Update()`;
- lane-target tweens in `AnimationManager`.

A safer first step is to replace the parallel arrays and repeated switches with an ordered lane definition such as `{name, x, objects}` and derive movement limits from a current lane index.

### Add an animation

Create the tweens in `AnimationManager`, chain them explicitly, and define whether they change gameplay transforms or only child poses. Gameplay actions need a flag or other guard if inputs must be blocked while the chain runs. Remember that:

- `TWEEN` is a global supplied by `game.html`, not an ES-module import;
- active tweens are stopped and restarted by pause;
- game over eventually calls `TWEEN.removeAll()`;
- changing the player hierarchy changes its dynamic `Box3` collision bound.

For a purely visual imported animation, the project would need new `AnimationMixer` integration; none exists today.

### Add a gameplay rule

Rules that react to overlap belong in `CollisionsDetector`. Rules that affect approach speed or spawn spacing belong in `WorldManager`. Input mapping belongs in `ControlManager`, while animation details belong in `AnimationManager`.

For nontrivial changes, introduce a dedicated game-state object instead of adding more module-level counters. That makes restart, testing, maximum lives, and state transitions explicit and avoids coupling UI output to collision history.

### Add an asset to initial loading

Use the `THREE.LoadingManager` passed from `main.js` when the asset must be ready before play begins. Runtime spawn classes currently create private managers, so their assets do not participate in the initial loader. Consider preloading and cloning frequently spawned meshes instead of parsing the same OBJ repeatedly.

## Known limitations and maintenance risks

- **Unbounded object retention:** passed and collected wrappers are hidden but never removed from the scene or lane arrays, and their geometries/materials are never disposed.
- **No object pooling:** every nonempty spawn constructs loaders and a fresh object hierarchy; dormant `unused` code does not implement reuse.
- **Increasing collision work:** every retained wrapper remains in the per-frame lane scan while the player is not invulnerable.
- **Long initial load:** 50 separate glTF loads are started, each parsing the full cave scene before extracting `stalagmite_2`.
- **Accumulating timers:** hit blinking installs a repeating reset interval, and the game-over branch installs another `TWEEN.removeAll()` interval on every rendered game-over frame.
- **Frame-sensitive spawn gate:** the distance limit is time-based, but the 20% spawn-attempt gate runs once per frame.
- **No difficulty scaling:** speed, spawn selection, and separation ranges remain constant.
- **Uncapped lives:** every heart increases the displayed effective-life total, including at full health.
- **Empty spawn outcome:** 12% of accepted spawn events create a wrapper without a gameplay model or type.
- **Desktop-only gameplay input:** there are no touch or swipe bindings for movement or jumping.
- **No persistence or audio:** score is memory-only and the repository contains no game audio.
- **No failure UI:** loader callbacks do not provide a visible fallback for failed assets.
- **Path coupling:** absolute `/NinjaAndLava/` script paths make root hosting or renamed directories fail without edits.
- **Legacy markup:** the HTML files contain malformed or stray doctype text, empty titles, and unresolved `base` placeholders that browsers currently recover from.
- **Dormant code and assets:** the old glTF lava loader points to missing files, rock spawning is commented out, and several stored image/source assets are not used at runtime.
